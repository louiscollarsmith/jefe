# LLM Runtime and Prompt Audit

Date: 2026-08-21  
Scope: repository evidence only, no production data inspection, no prompt or runtime changes.

## Executive Summary

Jefe has one shared structured-text LLM abstraction plus three direct model-backed paths outside that abstraction:

- Structured text generation: `apps/shopify/app/lib/llm/provider.server.js`.
- Multimodal attachment reading: `apps/shopify/app/lib/attachments/read-attachment.server.js`.
- Voice transcription: `apps/shopify/app/lib/llm/transcribe-voice.server.js`.
- Episodic-memory embeddings: `apps/shopify/app/lib/merchant-memory/embedding.server.js`.

The active runtime has more than the older "7 calls" operational notes imply. I found 16 runtime text interpretation/generation call sites, plus direct attachment, voice, and embedding model calls, plus several development/eval-only live-model scripts.

Highest anchoring risk is concentrated in four areas:

1. `agentic_recommendation`: before the first model turn Luna sees Merchant Memory, prior recommendations, action memory, and `initiallyRetrievedShopifyTools`. The initial Shopify API retrieval is lexical, not embedding-based, but the fallback query explicitly includes `products collections inventory merchandising discounts metafields`, and generated operation descriptions such as `collectionCreate` are model-visible before the model has independently formed a hypothesis.
2. Plan generation: `merchant-plan/prompt.server.js` is prescriptive by design. It requires at least one executable Shopify write and constrains recommendations to deterministic `opportunityCandidates`. That prevents generic advice, but it also teaches the model to choose within the supplied executable action surface rather than discover freely.
3. Conversation/memory retrieval: recent assistant messages, previous recommendations, action memory, conversation summaries, and model-generated store-understanding beliefs can re-enter later LLM prompts. Most are labelled by source/authority, but they can still self-anchor future turns.
4. Eval material: most fixtures/scenarios are test/eval-only and protected by test-time external-call guards. The main accidentally runtime-visible source is not test fixtures, but stored runtime history generated by earlier model outputs.

The old onboarding/bootstrap prompt template still exists, but the active helper returns `retired_agentic_recommendation_only`; I did not find a live provider call using `buildBootstrapPrompt`.

## Model Configuration

Source of truth: `apps/shopify/app/lib/llm/config.server.js`.

Defaults:

| Config | Current code default |
| --- | --- |
| Memory provider/model | `openai` / `gpt-5.6-luna` |
| Chat provider/model | `openai` / `gpt-5.6-luna` |
| Fallback provider/model | unset unless env provides both provider and model |
| Timeout | 30000 ms default |
| Max input tokens | 18000 default |
| Max output tokens | 900 default, overridden per call |
| Retries | `LLM_MAX_RETRIES`, default 1, so two attempts total |
| Groq input cap | `LLM_GROQ_MAX_INPUT_TOKENS`, default 6000 |
| Gemini input cap | `LLM_GEMINI_MAX_INPUT_TOKENS`, default 18000 |
| Embedding model | `gemini-embedding-2`, 768 dimensions |
| Embedding timeout | 5000 ms |

Environment examples in `apps/shopify/.env.example` match the current Luna default. `docs/ops/deployment_staging_railway_neon.md` is stale for staging examples: it still shows Groq primary / Gemini fallback, `LLM_TIMEOUT_MS=8000`, `LLM_MAX_INPUT_TOKENS=6000`, and `LLM_FALLBACK_MODEL=gemini-3.5-flash-lite`.

Provider behavior:

- OpenAI/OpenAI-compatible: chat-completions JSON schema, `store: false`, `reasoning_effort: "low"`. The generic OpenAI-compatible adapter adds `temperature: 0` and `top_p: 0.1` for non-OpenAI providers; first-party OpenAI omits those sampling overrides.
- Groq: `/openai/v1/chat/completions`, `temperature: 0`, `top_p: 0.1`, `reasoning_effort: "low"`, `max_completion_tokens`, local token-budget coordinator, immediate fallback on rate limit.
- Gemini: `models.generateContent`, `temperature: 0`, `topP: 0.1`, `candidateCount: 1`, `responseMimeType: "application/json"`, `responseSchema`.
- Fallback: only constructed when both fallback provider and model are configured and differ from primary. Fallback is used for provider availability errors, provider input cap failures, timeouts, 401/403/404/413/429/498/5xx, network/capacity errors. Validation failures do not trigger fallback.

## Prompt Assembly Diagrams

### Agentic Recommendation

```text
buildAgenticRecommendationSnapshot
  -> completed goals
  -> latest full insights
  -> up to 40 active beliefs with 2 evidence rows
  -> up to 8 prior recommendations
  -> retrieveMerchantContext(task="agentic_recommendation", tokenBudget=8000)
buildRecommendationContext
  -> merchantMemory {goals, insights, beliefs, merchantContext, previousRecommendations}
  -> boundedStoreEvidence privacy/source metadata
  -> searchableShopifyApiKnowledge instruction
  -> initiallyRetrievedShopifyTools from lexical Shopify API retrieval
system prompt
  -> semantic Shopify Action instruction
  -> no historical action-type constraint
  -> tool-use rules and read-before-recommend validation
iteration prompt
  -> promptVersion
  -> iteration
  -> merchantMemory
  -> boundedStoreEvidence
  -> searchableShopifyApiKnowledge
  -> initiallyRetrievedShopifyTools
  -> previousAttemptDiagnostics
  -> public toolResults from prior iterations
model
  -> tool calls or semantic recommendation
app
  -> runs retrieve/call tools, validates investigation and ids, persists recommendation/action
```

Ordering risk: `initiallyRetrievedShopifyTools` arrives before the first model response. It is derived from goal titles plus the first 12 beliefs, or from the fallback query `products collections inventory merchandising discounts metafields`. This can make Shopify operation categories salient before the model states a hypothesis.

## Actual Prompt Templates and Model-Visible Context

This section records the effective static prompt templates and dynamic fields. Full source is in the referenced files; schemas are also model-visible through provider response-schema/json-schema payloads.

### Shared Provider Envelope

All shared structured text calls are sent as:

- System message / Gemini `systemInstruction`: `request.systemPrompt`.
- User message / Gemini `contents`: `request.prompt`.
- Structured output schema: `request.schema`.

The provider estimates tokens from `systemPrompt + "\n\n" + prompt`, applies call-specific or config-level input/output caps, and records usage without logging prompt or response bodies.

### Agentic Recommendation Static System Prompt

Source: `apps/shopify/app/lib/shopify/agentic-runtime/recommendation-agent.server.js`.

Key exact rules:

```text
You are Jefe, deciding the most valuable concrete Shopify Action to recommend to this merchant.

You have Merchant Memory, bounded commerce evidence, Shopify read tools and a searchable generated catalogue of what the current Shopify Admin API can do.

Find a specific, evidence-backed outcome that Jefe can plausibly achieve through Shopify after the merchant accepts it. Do not constrain yourself to historical Jefe action types such as dead stock, restock, listing copy, tidy-up or markdown.
```

Dynamic fields:

- `merchantMemory`: goals, insights, active beliefs, merchant context, previous recommendations.
- `boundedStoreEvidence`: privacy/source metadata.
- `searchableShopifyApiKnowledge`: instruction to use generated Shopify API operation catalogue.
- `initiallyRetrievedShopifyTools`: lexical retrieval results with operation, kind, domain, description, scopes, arguments, tags.
- `previousAttemptDiagnostics`: retry diagnostics.
- `toolResults`: public results from previous iterations.

Prompt philosophy: mixed. Evidence-first in instructions, but tool surface is visible early and can bias hypothesis formation.

### Agentic Shopify Execution Static System Prompt

Source: `apps/shopify/app/lib/shopify/agentic-runtime/execution-agent.server.js`.

Key exact rules:

```text
You are Jefe executing an Action that the merchant has accepted.

Your objective is the ACCEPTED ACTION OUTCOME. You have generated Shopify Admin API read/write tools, and every call goes through the server gateway.
```

Dynamic fields:

- `acceptedActionRevision`.
- `acceptedAction`: semantic outcome, scope, constraints, expected effects, verification plan.
- `initiallyRetrievedShopifyTools`: derived from accepted outcome/scope/effects.
- `toolResults`: public previous gateway results.

Prompt philosophy: prescriptive execution policy, appropriate after acceptance.

### Agentic Action Chat Static System Prompt

Source: `apps/shopify/app/lib/shopify/agentic-runtime/action-chat.server.js`.

Key exact rules:

```text
You are Jefe collaborating with the merchant on one proposed Shopify Action.

The Action has NOT been accepted unless action.lifecycle.accepted is true. Before acceptance you may inspect the semantic Action and investigate Shopify using read operations.
```

Dynamic fields:

- `merchantMessage`.
- `recentMessages` last 8.
- `pendingClarification`.
- `action`: public semantic action state.
- `tools`: hardcoded chat tool catalogue.
- `toolResults`: last 16.

Prompt philosophy: evidence-first for refinement, prescriptive around acceptance/write boundary.

### Merchant Plan Static System Prompt

Source: `apps/shopify/app/lib/merchant-plan/prompt.server.js`.

Key exact rules:

```text
Choose exactly one recommendation.
...
JEFE MVP RULE:
A valid recommendation must lead to at least one meaningful Shopify write performed by Jefe.
...
Do not invent a candidate not present in opportunityCandidates.
```

Dynamic fields:

- allowed goal/belief/insight ids.
- executable Shopify write capabilities.
- support capabilities and complete step capability catalogue.
- output-contract examples for candidates, selected recommendation, workflow, success signal.
- full snapshot including deterministic `opportunityCandidates`.

Prompt philosophy: prescriptive. This is deliberate product behavior but can anchor Luna toward executable Shopify-write opportunities over advice/instruction paths.

### Merchant Insights Static System Prompt

Source: `apps/shopify/app/lib/merchant-insights/prompt.server.js`.

Style: evidence-first with negative examples. It bans unsupported terms like "premium", "curation", "customer base", "marketing approach", "operational risk", and "strategy" unless cited beliefs directly support them.

Dynamic fields:

- `allowedSupportingBeliefIds`.
- `beliefFieldLegend`.
- `snapshot` of active beliefs.
- `validationNotice` on retry.
- output-contract example.

Prompt philosophy: evidence-first, with concrete anti-pattern examples. Anchoring risk is low to medium: examples mostly constrain unsupported generic language rather than suggest actions.

### Merchant Goals Static System Prompt

Source: `apps/shopify/app/lib/merchant-goals/prompt.server.js`.

Style: mixed. It uses Merchant Memory, but includes concrete transformation examples for merchant coaching such as turning a bare revenue target into a more grounded commercial goal.

Dynamic fields:

- beliefs and insights.
- `goalCoaching` from typed merchant input or uploaded document summaries.
- output-contract examples for 3/6/12 month horizons.

Anchoring risk: medium for revenue/growth phrasing because the prompt explicitly requires commercial outcome terms in every title.

### General Grounded Chat Static System Prompt

Source: `apps/shopify/app/lib/merchant-memory/general-chat.server.js`.

Key instructions:

- Use only the supplied Merchant Context packet.
- Current authoritative semantic memory outranks older episodes.
- Historical items are labelled and must never be described as current.
- Never claim performed action unless action-ledger item says so.
- Use `currentAction` before generic memory for focused action questions.
- Return citations only from packet ids.

Dynamic fields:

- merchant message.
- current action duplicate.
- recent messages from working memory last 8.
- full Merchant Context packet.

Prompt philosophy: evidence-first. Self-anchoring risk is medium because working memory and episodic/action memory can include prior assistant outputs.

### Passive Memory Decision Static System Prompt

Source: `apps/shopify/app/lib/merchant-memory/passive-memory.server.js`.

Key instructions:

- Classify into `acknowledge_memory`, `commerce_analysis`, `historical_recall`, or `general_chat`.
- Use only supplied registry keys.
- Ordinary anecdotes and assistant statements are not durable memory.
- Use `policies.never_recommend` for strong rules without narrower key.

Dynamic fields:

- sanitized merchant message.
- top semantic memory.
- writable belief registry with guidance.

Prompt philosophy: evidence-first classifier with prescriptive registry mapping.

### Memory Edit Structured Operation Static System Prompt

Source: `apps/shopify/app/lib/merchant-memory/conversation.server.js`.

Key instructions:

- Interpret merchant messages for Merchant Memory.
- Do not write to databases or claim update succeeded.
- Shopify-derived observations are not always merchant truth.
- Merchant corrections have authority, but raw observations and merchant policies stay separate.
- Resolve references against `recentThread`.
- Use only supplied supported belief keys.

Dynamic fields:

- merchant message.
- recent thread.
- conversation context.
- retrieved context.
- active beliefs selected by relevance and budget.
- open questions.
- supported belief definitions.

Prompt philosophy: evidence-first, but context-rich.

### Commerce Analyst Planner and Reply Static Prompts

Source: `apps/shopify/app/lib/merchant-memory/commerce-analyst.server.js`.

Planner:

- Read-only commerce analysis.
- Use only supplied catalog.
- Prefer aggregates first.
- Treat evidence states (`NOT_INGESTED`, `UNKNOWN`, `INSUFFICIENT_EVIDENCE`, `UNAVAILABLE`) as binding.
- For reorder/restock quantities, request stock-cover and derive units via the supplied formula.

Reply:

- Use only action context, recent thread, and computed analyst packet.
- Give quantitative recommendation when packet supports it.
- Do not invent facts.
- Optional chart values must already appear in packet.

Prompt philosophy: prescriptive but grounded. Anchoring risk medium for replenishment because the planner includes a hard-coded 30-day cover default and formula.

### Store Understanding Static System Prompt

Source: `apps/shopify/app/lib/merchant-memory/store-understanding.server.js`.

Key instructions:

- Use only registered belief keys.
- Every candidate grounded in bounded store summary.
- Use cautious language; provisional LLM-derived inferences for merchant confirmation.

Dynamic fields:

- registry of low-authority belief definitions, descriptions and `promptGuidance`.
- bounded store summary.

Prompt philosophy: evidence-first with registry-shaped ontology. Risk medium around `brand.apparent_positioning`, whose allowed enum includes `premium`, `value`, `specialist`, `convenience`, `unclear`.

### Focused Action Agent Static System Prompt

Source: `apps/shopify/app/lib/actions/agent/agent-loop.server.js`.

Dynamic system prompt changes based on available tools. Examples:

- If `draft_supplier_email` is available, the prompt says a request to draft the supplier email should call that tool unless explicitly negated.
- If `update_plan` and `simulate_plan` are available, it distinguishes persistent changes from hypotheticals.
- If `replan_action` is available, it lists structural workflow-change examples.

Dynamic fields:

- merchant message.
- recent messages last 8.
- pending clarification.
- action state.
- narrowed tool catalogue.
- this-turn tool ledger.

Prompt philosophy: prescriptive action interpreter. Anchoring risk medium to high within focused action workflows because examples teach specific "when you see X, call Y" mappings.

### Action Replanner Static System Prompt

Source: `apps/shopify/app/lib/actions/action-replanner.server.js`.

Style: prescriptive. It includes many workflow examples: purchase orders are not transfers, final/last ordering, remove step N, correction wording, etc.

Dynamic fields:

- merchant instruction.
- recent conversation last 10.
- current action and plan values.
- current workflow with position.
- current artifacts and current proposal.
- available capabilities.

Anchoring risk: high for workflow-shape decisions, low for merchant/store recommendation choice because this path only runs after a merchant asks to change an existing action.

## Tool Descriptions and Retrieval Bias

### Generated Shopify API Retrieval

Source: `apps/shopify/app/lib/shopify/api/retrieval.server.js`.

Retrieval is lexical, not model-backed:

- Query is tokenized by non-alphanumeric boundaries.
- Score adds operation +8, domain +5, tag +4, description +2.
- Returns operation, kind, domain, description, scopes, arguments, tags, matched terms, score.

The model sees generated operation descriptions. Examples from `apps/shopify/app/lib/shopify/api/catalogs/shopify-admin-api-2026-07.generated.json`:

- `collectionCreate`: "Creates a Shopify collection for merchandising products together."
- `collectionAddProducts`: "Adds products to an existing manual collection."
- `productVariantsBulkUpdate`: includes pricing fields.
- `discountCodeBasicCreate`: creates a discount code and can affect pricing/promotions.

Bias risk:

- The agentic recommendation initial fallback query explicitly includes `collections` and `merchandising`, so collection tools can appear before merchant evidence establishes a merchandising hypothesis.
- In normal non-empty snapshots, initial query comes from goals and first 12 beliefs. If those beliefs contain product/category/inventory language, relevant tool classes surface early. This is useful, but still tool-salience before explicit hypothesis.
- The model can later call `retrieve_shopify_operations` with its own query, so hypothesis and retrieval can influence each other in the same loop.

### Focused Action Tool Catalogues

The focused action agent receives narrowed action-kind tools from `tool-registry.server.js`. Tool descriptions are concrete and action-shaping:

- `inspect_current_proposal`: tells the model this is always available.
- `replan_action`: tells the model to rebuild workflow from merchant semantic instruction.
- supplier/replenishment/product-type tools create strong action-local mappings.

These are appropriate for action operation, but they are not evidence-neutral.

## Test and Eval Isolation

`apps/shopify/app/lib/llm/external-call-guard.server.js` disables external LLM calls when:

- `JEFE_EXTERNAL_LLM_DISABLED=true`;
- `NODE_ENV=test`;
- `NODE_TEST_CONTEXT` is set;
- the process uses `--test`.

`apps/shopify/tests/llm-test-isolation.test.mjs` asserts real Groq, OpenAI, Gemini, embeddings, and voice transcription cannot call external providers under Node test without injected transports.

Questionable sources:

| Source | Runtime reachable | Why |

| `apps/shopify/scripts/answer-quality/*` | CONDITIONAL development only | Calls real `sendGeneralChatMessage` against local seeded DB; not app runtime, but can use real provider if env enables it |

## Hidden Self-Anchoring

The following loops exist:

```text
LLM recommends semantic Shopify Action
-> recommendation/action persisted
-> action memory and previousRecommendations retrieved
-> future agentic recommendation/general chat sees prior recommendation
-> recommendation concept can become more salient
```

```text
assistant chat reply
-> stored as conversation message
-> working memory / episodic memory retrieves it
-> later LLM sees prior assistant wording
-> wording can act as hidden few-shot or local precedent
```

```text
conversation summary LLM
-> summary episode stored
-> vector/lexical retrieval returns summary
-> later chat or recommendation sees compressed prior model interpretation
```

```text
Store Understanding LLM
-> inferred belief persisted with llmInference precedence
-> semantic memory retrieves belief
-> future insights/goals/plan/chat see it beside deterministic beliefs
```

Separation mechanisms:

- Beliefs carry status, confidence, precedence, evidence, source, authority and temporal status.
- Store Understanding persists with `BELIEF_PRECEDENCE.llmInference`.
- Conversation summaries are prompted not to turn Jefe suggestions into merchant facts.
- Merchant corrections and confirmations outrank inference.
- General chat tells the model current semantic memory outranks older episodes and historical items must remain historical.

Residual risk:

- The model sees many context items as plain content after labels. Even with source labels, repeated prior assistant recommendations can make the same action feel more supported.
- `previousRecommendations` in agentic recommendation only include id/title/summary/reviewStatus. They do not include a strong "model-generated, not evidence" warning per row.
- `actionMemory` content for recommendations is title + summary, which can be persuasive prose.

## Diagnostic Findings

### High

1. Agentic recommendation can see Shopify operation concepts before hypothesis formation.
   - Evidence: `buildRecommendationContext` inserts `initiallyRetrievedShopifyTools`; fallback query includes `products collections inventory merchandising discounts metafields`.
   - Mechanism: lexical generated API retrieval over operation descriptions/tags.
   - Impact: collection/discount/inventory concepts can become salient before merchant evidence independently points there.

2. Runtime history creates hidden few-shot examples.
   - Evidence: `retrieveActionMemory`, `retrieveWorkingMemory`, `retrieveEpisodicMemory`, `previousRecommendations` in agentic snapshot.
   - Mechanism: prior model outputs return as context.
   - Impact: repeated recommendations/actions may reinforce themselves unless source/authority wording is strong enough.

### Medium

3. Plan generation is intentionally executable-opportunity constrained.
   - Evidence: Merchant Plan prompt requires one meaningful Shopify write and forbids candidates outside `opportunityCandidates`.
   - Impact: good for MVP actionability, but not neutral discovery.

4. Focused action prompts include concrete phrase-to-tool examples.
   - Evidence: `buildActionAgentSystemPrompt` and `ACTION_REPLANNER_SYSTEM_PROMPT`.
   - Impact: appropriate local behavior, but overtraining-like patterns can occur inside action chat.

5. Store Understanding registry can introduce ontology bias.
   - Evidence: registry descriptions/guidance and allowed enum values are included in the prompt.
   - Impact: model chooses among supplied categories; low-authority inference status reduces but does not remove downstream salience.

### Low

6. Archived prompts and most tests are not production-visible.
   - Evidence: no active imports found; test external-call guard.
   - Impact: low unless copied into runtime manually.

7. Old bootstrap prompt is not active.
   - Evidence: no provider call; `generateBootstrapAlternative` returns retired status.
   - Impact: low.

## Recommendations for Follow-Up Investigation

No runtime changes were made in this audit. Follow-up questions to decide before changing prompts or retrieval:

1. Should agentic recommendation receive `initiallyRetrievedShopifyTools` only after it emits evidence-backed hypotheses?
2. Should previous recommendations/action memory be split into `merchant-approved/executed` versus `model-suggested` sections in every prompt?
3. Should generated Shopify API retrieval exclude mutations during recommendation hypothesis formation until a hypothesis names the needed effect?
4. Should `previousRecommendations` include supporting evidence ids and source labels, or be withheld from first-pass recommendation generation?
5. Should prompt examples in Goals, focused action, and replanner be converted from concrete outputs to abstract decision rules where possible?
