# Part 11 — Were stable Shopify IDs available to the model?

```text
STABLE_ID_AVAILABLE_TO_MODEL: YES — but it was the wrong ID.
```

Merchant Memory's `products.bestseller_by_revenue.trailing_90d` and
`products.product_momentum.trailing_60d` beliefs (both cited in `reactivate-sales-after-gap`'s
`businessEvidenceRefs`) each carry a field named exactly `productId`:

```json
{ "title": "Borderlands Discovery Four", "productId": "e00fb90c-15a8-44ed-8fce-d702e11c2322", "revenue": 444, ... }
{ "title": "Cloud Needle Tsolikouri", "productId": "15523d15-581c-4e80-80c3-bdb36a524dc8", ... }
```

These values are **our own internal `products.id`** — a local Postgres primary key, generated by
`gen_random_uuid()`, used throughout `app/lib/merchant-memory/shopify-derivations.server.js` purely
for joining orders/line-items/variants to their product. They are coincidentally UUID-shaped, exactly
like a Shopify GID's opaque suffix can be, which is precisely why the model could not tell the
difference: nothing about the string `e00fb90c-15a8-44ed-8fce-d702e11c2322` signals "internal
database key" rather than "Shopify identifier."

The real Shopify GID was available the entire time, one field over, unused:
`products.external_id` (already stored as `gid://shopify/Product/10375207780648`) — but it is never
surfaced into belief `value_json` anywhere in this file. The model was never shown it.

## `WHY_NOT_USED`

Not a model reasoning failure — a data-availability failure. The model did exactly what a reasonable
agent should do with a field literally named `productId` sitting next to the product's own title in
its highest-authority evidence source (a `deterministic`-authority Merchant Memory belief): it used
it as the identifier. It could not have "preferred the real Shopify GID" because the real Shopify GID
was not in the belief it was given — this is not a case of the model ignoring a better option.

## Design implication (confirmed, not merely potential)

> known Shopify ID → prefer direct node/product lookup, instead of known Shopify object → fuzzy
> textual search

is the *right instinct* the model already has (Attempts B and C both reached for a direct `nodes(ids:
)` lookup before falling back to title search) — the defect is entirely upstream, in what belief
construction serializes as `productId`. Fixed in `12` by resolving to `products.external_id` at every
belief-construction site that emits a product reference, rather than by telling the model to be more
suspicious of ids it's handed (which would be a prompt-level patch over a data-quality bug).

## Scope check: is this pattern isolated to products?

Searched `app/lib/merchant-memory/shopify-derivations.server.js` for the equivalent pattern
(`variantId,` / `orderId,` / `customerId,` as a bare shorthand property paired with a lookup) —
**none found**. The bug is scoped to the 7 product-reference call sites fixed in this pass (all in
this one file); no evidence of the same class of leak for variants, orders, or customers in this
file. Not exhaustively audited across every merchant-memory module — flagged as a narrow follow-up in
`12`, not fixed here per this task's "smallest correct fix" instruction (fixing an unproven, undemonstrated case elsewhere would not meet the "conclusively proven" bar).
