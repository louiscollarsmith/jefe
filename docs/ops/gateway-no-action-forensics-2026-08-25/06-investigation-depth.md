# Parts 7, 8, 11, 12 — Investigation depth, termination authority, mutation discoverability

## Did Luna itself choose to stop, or did something else terminate the candidate?

For all 6 candidates: **the model itself concluded each candidate was blocked**, based on the tool
result it received. There is no evidence of a deterministic gate, turn-budget, or global-budget
cutoff terminating any candidate early — every `TRYING_NEXT_CANDIDATE` / terminal disposition in
`progressLog` carries a specific, evidence-citing `reason` string generated by the model interpreting
a real (if, for 2 of the underlying reads, wrong) tool result.

Termination authority per candidate:

| Candidate | Termination authority |
| --- | --- |
| `reactivate-sales-after-gap` | `MODEL_DECISION` (accepted the empty `products` read as conclusive) |
| `improve-customer-retention-measurement` | `MODEL_DECISION` (never issued its own on-topic query at all — see below) |
| `raise-items-per-order` | `MODEL_DECISION` (inherited via `ALREADY_AVAILABLE`, did not re-query) |
| `recover-declining-product-demand` | `MODEL_DECISION` (same) |
| `restore-unavailable-variants` | `MODEL_DECISION` (issued its own query, accepted the empty result) |
| `capture-product-margin-data` | `MODEL_DECISION`, correctly — real data confirmed the blocker |

No `EVIDENCE_GATE`, `EXECUTION_GATE`, `NOVELTY_GATE`, `SCHEMA_VALIDATOR`, `AUTHORIZATION`,
`TURN_BUDGET`, or `GLOBAL_BUDGET` termination occurred this run. The one `PROVIDER_FAILURE` (the
0-token error at 18:06:37) did not terminate a candidate — the retry at 18:06:45 succeeded and the
run proceeded normally into the rescue pass 6 seconds later.

## Investigation depth: did Luna refine the query when the first attempt was insufficient?

**No, for 4 of 6 candidates.** Once the first `products` search came back empty,
`reactivate-sales-after-gap` did not retry with a different query shape, and the three candidates that
reused that same result via `ALREADY_AVAILABLE` never issued a query of their own at all —
`improve-customer-retention-measurement` in particular needed an **orders/customers** read to answer
its own stated question ("can orders be linked to customer identities?") and never issued one; it
reasoned from an unrelated `products` read instead. `restore-unavailable-variants` did issue a
second, differently-scoped query and also stopped after one empty result.

This is the "investigation terminates too early" pattern the task asked to name precisely (Part 18).
It is real, and it is the dominant defect this run — not a missing capability, not a missing scope,
not a runtime budget limit.
