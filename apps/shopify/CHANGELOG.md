### Performance

- **`app._index` decomposition — move 1: `DailyHome` is now code-split.** The returning-user home (`DailyHome`, ~35kB client / 50kB server, hand-rolled, zero Polaris) renders **only** for `appMode === "daily"`, yet it was statically imported into the 4.6k-line `app._index` route module — so **every first-run onboarding and memory-view user downloaded it for nothing**. It's now `React.lazy` + `Suspense`; because the app streams SSR, the server still resolves and streams the real `DailyHome` HTML for daily users (React selective hydration keeps that server markup in place — no fallback flash, no CLS, LCP preserved). Net: the `app._index` route chunk drops **85.8 → 51.5 kB raw (21.8 → 13.9 kB gzip)** and `DailyHome` splits into its own **35.4 kB (8.83 kB gzip)** chunk fetched only in daily mode. Behaviour-preserving, no schema change; full gate green (0 failures) and the build confirms the split. First move of the perf-first `app._index` decomposition (addresses the returning-user LCP/interaction pain). `app/routes/app._index.tsx`. Next moves: code-split the onboarding step components and lazy-load `MerchantMemoryView`, each coordinated with the session that owns that region.

### Fixed

- **Duplicate `app/uninstalled` no longer leaves a churned shop `active` (bug).** A retried uninstall webhook hit `ensureShopifyTenant` — which reactivates an "uninstalled" shop back to "active" — *before* the dedupe short-circuit returned "duplicate", so a redelivery left the shop stuck `active`, corrupting the churn signal and the retention/GDPR posture. `app/uninstalled` is now handled *before* the dedupe check: churn is captured once (gated on `created`) and `markShopifyInstallInactive` is **always** re-asserted (idempotent). Also adds the additive nullable `Shop.uninstalledAt` (migration `20260729130000_shop_uninstalled_at`), set on inactivation. `app/lib/ingestion/shopify/webhooks.server.js`; regression test in `tests/shopify-ingestion.test.mjs`.
- **Post-deploy alert noise cut: streaming aborts + startup DB blips no longer page.** Benign, deploy-correlated signals that were paging #jefe-slack now log WARN instead: streaming render errors from client aborts / premature-close / ECONNRESET (`isBenignStreamError`), readiness/health/worker DB-connection blips within a post-deploy grace window (`READINESS_ALERT_GRACE_SECONDS`, default 60s, while the Prisma engine + Neon pool warm), and bot `POST /` 4xx. Real failures after the grace window still page. `app/lib/observability/stream-errors.server.js`, `app/services/deployment-health.server.js`, `app/entry.server.tsx`.
- **Backfill loop pages only on a SUSTAINED failure, not a single transient blip.** The Shopify backfill loop retries every tick, so one failed tick — a Neon connection drop, a deploy warmup, or a Prisma engine blip like `Response from the Engine was empty` — self-heals on the next tick and no longer pages #jefe-slack; it logs WARN with the failure streak. Only once the consecutive-failure streak reaches `BACKFILL_LOOP_PAGE_AFTER` (default 3 ≈ 45s at the 15s tick) does it page (ERROR + `worker_error` event) — a genuine sustained outage. Replaces the worker's earlier grace-window + Prisma-error-string classifier (which let unrecognised transient variants through and page), and is **error-agnostic** so no new engine-error string can slip past. `app/services/shopify-backfill-worker.server.js`, `app/services/deployment-health.server.js` (`shouldPageOnWorkerError` now takes the streak; the unused `isTransientDbConnectionError` removed); `tests/deployment-health-grace.test.mjs`.
